# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this pipeline does

`xenium_nb` is a Nextflow pipeline for Xenium spatial transcriptomics analysis. All steps run through a single entry point, `main.nf`, selected with `--step`:

- `downsample_xenium_region` — crops a raw Xenium output directory to a bounding box region
- `create_sdata` — converts raw Xenium output into a sample-level SpatialData zarr artifact. Annotates per-cell (`n_genes_by_transcripts`, `pct_transcripts_in_top_{5,10,20,50}_genes`, `control_counts`, `pct_control`, `transcripts_per_gene`, `nucleus_ratio`) and per-gene (`n_cells_by_transcripts`, `mean_transcripts`, `pct_dropout_by_transcripts`, `total_transcripts`, `codeword_category`) QC metrics but **filters nothing** — like `create_adata`, it produces the raw artifact and leaves thresholds to downstream analysis. Computing them here reads X once, at the only point it is already in memory, so a QC report can work from `obs`/`var` alone. Three details are Xenium-specific and easy to get wrong:
    - **`expr_type="transcripts"`, not the default `"counts"`.** The Xenium reader already puts a `total_counts` in `obs` from `cells.parquet`, and it is **not** a row sum of X — it is `transcript_counts` + the five control/codeword counters. The default `expr_type` would silently overwrite it with `X.sum(axis=1)`, destroying that meaning. Renaming the outputs sidesteps the collision. `cluster_sdata` and `cluster_sdata_gpu` used to clobber it this way and no longer recompute anything (see below); `cluster_sdata_gpu_ooc` still does
    - **Threshold on `transcript_counts`, never `total_counts`** — the latter includes negative controls, so a cell with 8 real transcripts and 4 deprecated codewords survives a `min_counts=10` cut. `transcript_counts` equals `X.sum(axis=1)` exactly. **It is also qv-filtered, which is easy to assume the other way round**: 10x builds the cell-feature matrix only from molecules passing the qv 20 cut, so `transcript_counts` is exactly the count of transcripts where `is_gene AND cell_id != "UNASSIGNED" AND qv >= 20` — verified on an uncropped test bundle, where that count matches for 100.000% of cells (101,378,978 both sides), while counting every molecule regardless of qv matches 0.27%. The threshold is inclusive: `qv > 20` matches only 82%. The practical consequence is that a below-qv molecule is **absent from X**, not a marginal contributor to it — so the share below threshold measures decode failure and data lost before counting, not contamination of the counts (~8% of decoded molecules on one test ROI). The redundant `obs["total_transcripts"]` that `calculate_qc_metrics` emits is dropped for this reason; per-gene `var["total_transcripts"]` is a different quantity and is kept
    - **`var["codeword_category"]` is a lookup, not a summary**, which is what makes it safe to compute here alongside the metrics. `feature_name` → `codeword_category` is strictly one-to-one (verified: 0 of 7,415 features on a test ROI carry two), so collapsing the molecule table with `drop_duplicates` loses nothing — and it is a single cheap pass rather than a `groupby`, which matters when a whole-slide sample has hundreds of millions of molecules (1.5 s over 6.9M on a test ROI, reading only the two columns). Only the **gene** categories reach `var`, since controls are not features in X: it resolves to `predesigned_gene` vs `custom_gene` (4,995 / 100 on a test ROI), which is the one question the per-gene abundance and detection metrics cannot answer — whether separately-designed custom probes land in the same abundance-detection cloud as the catalogue ones. A gene with **no transcript anywhere in the sample** has no row to read from and is left unmapped (6 on a test ROI); that is a real state, distinct from the ~30 genes detected in no *cell*, and is kept rather than filled. The column is written as a **`pd.Categorical`**, and that is load-bearing rather than tidiness: an object column of strings-plus-`None` goes through **spatialdata's** writer as a plain `vlen-utf8` string array and `None` is coerced to the literal string `"None"` — verified on a real ROI, where the three unmapped genes came back as a third category and `isna()` returned 0, silently turning "no transcript anywhere" into a label. A categorical is stored as codes plus categories with `-1` for missing, so the gap round-trips as a genuine NA. (Note `anndata.write_zarr` handles the object column correctly on its own; it is the spatialdata path that does not, so testing the round-trip through anndata alone will not catch this.) Categorical also keeps comparisons safe: `col == "custom_gene"` yields a plain bool mask with `False` at the missing entries, where a nullable string dtype yields `pd.NA` and raises `boolean value of NA is ambiguous` downstream. `qc_report` derives this itself today and should read it instead — that is the deck's only remaining reason to load the molecule table on a default render
    - **No `qc_vars`.** The panel carries no `MT-` genes at all, so `pct_transcripts_mt` would read 0.0 for every cell — a metric that looks real and passes any threshold. Ribosomal/hemoglobin sets are only partially and arbitrarily represented on a targeted panel (and naive `^RP[SL]`/`^HB` patterns match non-members like `RPS6KA5`, `HBEGF`, `HBS1L`), so they are omitted rather than reported as if comparable to scRNA-seq. Negative-control % cannot use `qc_vars` either — controls are not features in X, only `obs` columns — so `control_counts` (the sum of the five control/codeword counters) and `pct_control` are written explicitly instead. `pct_control`'s denominator is `transcript_counts + control_counts`, not `obs["total_counts"]`: the two are identical on this object, but `total_counts` is the column `cluster_sdata_gpu_ooc` overwrites with a plain row sum, whereas `transcript_counts` always equals `X.sum(axis=1)`. It is NaN, not 0, where a cell has neither transcripts nor controls (2 cells in one test ROI) — 0 would read as a clean cell. `cluster_report` used to derive this number itself; it now reads the column and has **no fallback** — a zarr predating it raises `KeyError` naming the missing columns, because a fallback is a second definition of the metric wearing a disguise and would let a stale cohort render numbers that came from outside the pipeline. The fix is to re-run `create_sdata`
    - **`percent_top` is `(5, 10, 20, 50)`, lower than `create_adata`'s `(10, 20, 50, 150)`** — a cell cannot detect more genes than the panel targets, and at a median 174 genes/cell, `top_150` pins 40% of cells at exactly 100%, inverting the metric so the emptiest cells score highest
- `create_adata` — converts a Cell Ranger `filtered_feature_bc_matrix` directory (scRNA-seq, not Xenium) into a sample-level `<sample>.h5ad`. Annotates per-cell/per-gene QC metrics (`total_counts`, `n_genes_by_counts`, `pct_counts_mt`, `percent_top`) but **filters nothing** — mirroring `create_sdata`, it produces the raw artifact and leaves thresholds to downstream analysis. Mito genes are auto-detected from the gene symbols with a case-insensitive `^[Mm][Tt]-` match (the same pattern used in the `oir-analysis` project), so human and mouse both work with no species flag. Output is a plain h5ad, so the `cluster_sdata*` steps (which read SpatialData zarrs) do **not** consume it — clustering scRNA-seq needs a new step
- `create_follicle_sdata` — subsets a sample zarr into per-cell follicle zarrs
- `cluster_sdata` / `cluster_sdata_gpu` — filter, normalize, PCA, neighbors, UMAP, Leiden clustering (CPU vs. RAPIDS/GPU). Neither **computes QC metrics** any more: `create_sdata` already annotated every per-cell and per-gene metric at the one point X was in memory, so both steps now only filter (`--min_counts`, default 10; `--min_cells`, default 5). Removing the redundant `calculate_qc_metrics` call is safe because `filter_cells`/`filter_genes` — scanpy's and rapids-singlecell's alike — derive their thresholds from X directly and never read `obs`; verified on a real ROI, the retained cells, retained genes, and all ten `leiden_res_*` columns are identical before and after. What it fixes is that the call ran with the default `expr_type="counts"` and so overwrote the Xenium-native `obs["total_counts"]`, and ran *before* `filter_genes`, leaving a value that described the full panel while the object shipped only the surviving genes (wrong for 802 of 21,719 cells on one ROI). Clustered zarrs therefore no longer carry `n_genes_by_counts`, `log1p_*`, or `pct_counts_in_top_*` — read `create_sdata`'s `n_genes_by_transcripts` and `pct_transcripts_in_top_*` instead. **Metrics on a clustered zarr are pre-filter by construction**, since they describe the raw artifact; the drift is negligible (mean transcripts/cell 277.74 vs 277.70) and it buys one definition of each metric everywhere
    - `cluster_sdata_gpu_ooc` is deliberately **not** part of this and still recomputes. Its filter reads `obs["total_counts"]`, which is correct *only because* its own `rsc.pp.calculate_qc_metrics` clobbers the column first — deleting the recompute without repointing that mask to `transcript_counts` turns accidental correctness into the exact bug described above. It also cannot simply inherit the gene-side metric: `anndata.concat` drops **all** `var` columns (obs survives whole), so the merged cohorts this step exists for arrive with an empty `var`, and cells-per-gene is a property of the merged object rather than of any one sample

All three `cluster_sdata*` steps **sweep Leiden resolutions** rather than committing to one. `--resolutions` takes a comma-separated list (`--resolutions 0.5,1.0,1.5`); the default sweep is `0.1` through `1.0` in steps of `0.1` (ten resolutions) and lives only in the Python scripts (`params.resolutions` is null in `nextflow.config`, and the modules omit the flag when it is unset, so the default is defined in one place). Each resolution gets its own obs column, `leiden_res_<r>` formatted to two decimals (`leiden_res_0.60`) — so two resolutions agreeing to two decimals (0.125, 0.126) collide on one column and the second silently wins; nothing checks for this. There is **no plain `leiden` column** — downstream code must select a resolution by name, and nothing records the sweep outside those columns. The sweep is cheap: neighbors/UMAP are computed once and only community detection re-runs per resolution — on a 21.7k-cell ROI, 0.4–1.6 s each on CPU and ~0.7–0.9 s on GPU, against ~19 s for the graph. It is cheap **only because no `n_iterations` is passed** (see below); pinning one previously cost the CPU step 6.4 s per resolution on that ROI and 82% of its total runtime on a 638k-cell sample.

All three run the **same fixed embedding recipe**, taken from 10x's Xenium Prime workshop vignette (which targets the same 5K panel): `seurat_v3` HVG on raw counts (2000 genes, flagged not subset) → `normalize_total` → `log1p` → `scale(zero_center=False, max_value=10)` → `pca(n_comps=30)` → `neighbors(metric="cosine")` → Leiden. Those steps are **constants in the scripts, not CLI flags** — they define what a cluster means here, and the three steps' labels are only comparable if they agree. Changing one is a change to the pipeline.

It was adopted on evidence, not authority. Holding filtering constant on both downsampled test ROIs, the previous recipe (no HVG, no scaling, 50 PCs, euclidean) produced 3 clusters on one ROI, one confident reference cell type, and marker-score separations of 0.010 — it did not isolate oocytes or granulosa at all — where this one produced 7 clusters, 3 types, and separations 5–6× higher; oocyte separation on the other ROI more than doubled (0.079 → 0.176). One deviation from the vignette is forced: the ooc step **flags** HVGs like the others rather than subsetting, so its `var` matches — `--n_top_genes` still hard-subsets when a merged cohort will not fit.

**No `n_iterations` is passed to Leiden in any of the three steps, and that is deliberate.** Each library's default already means "run to convergence" in its own idiom — scanpy's `-1` (iterate until a stable iteration) and rapids-singlecell's `100`, which cuGraph treats as a cap it exits early from (verified: `100` and `1000` give ARI 1.000000 and identical runtime). The two **cannot be made to agree by sharing a number**, because the parameter counts different things: igraph iterations are refinement passes over a complete partition, while cuGraph's are hierarchical levels. Measured on a 21,694-cell ROI, `n_iterations=2` leaves igraph slightly under-polished (ARI 0.86–0.90 against convergence) but gives cuGraph **~3,000 clusters instead of 4–11** (ARI 0.003).

The steps previously pinned `100` in all three, which came from writing the vignette's `-1` into the GPU step, hitting `OverflowError` (rapids forwards it to cuGraph as a `size_t`), and pinning rapids' default in both rather than dropping the argument. On GPU that was a no-op; on CPU it turned "converge" into a mandate of 100 refinement passes long after the partition stopped changing — 6.4 s per resolution against 0.4–1.6 s, and 6,824 s of a 8,271 s run on a 638k-cell sample. Removing it changes CPU labels slightly (ARI 0.985–0.998 against the old behaviour, same cluster counts at every resolution), so a sweep read before this change should be read again. GPU and ooc labels are unchanged — ooc never passed it at all.

Because scaling overwrites X, the written table carries **three expression forms**: `X` (scaled, what the embedding was built from), `layers["counts"]` (raw), and `layers["lognorm"]` (log-normalized). Anything reading expression rather than a reduced representation — `rank_genes_groups`, marker scoring, reference centroid correlation — must use `lognorm`; X is no longer expression after `scale`. (`cluster_sdata_gpu_ooc` omits `counts`, since holding a second copy of a merged cohort's matrix is what that step exists to avoid.)

The **filtering cut** stays parameterised: `--min_counts` (cells below that many transcripts), `--min_cells` (genes detected in fewer cells — **masked, not removed**, see below), and `--max_counts_quantile` (an upper cell cut at that quantile of transcript counts, targeting doublets and segmentation merges; 0 disables). Defaults are 10x's for the first two — **20 and 100** — and **0 for the upper cut, i.e. off** — and live only in `bin/cluster_sdata*.py`. The upper bound is a quantile rather than an absolute number because depth varies enough between samples that a fixed ceiling would be a different cut on each; it is computed on the **unfiltered** table, before `min_counts` removes the low tail, so the threshold does not move when the lower one does. **It defaults to off, and that reverses 10x's value deliberately.** At their 0.98 it removed *every* oocyte: against a hand-curated list of 117 putative oocytes in ROI1, all 48 and all 18 of those falling in the two test crops were cut, their median transcript count being ~5,000 against a threshold of ~700. Oocytes are the largest and most transcript-rich cells in ovary, so a top-percentile cut aimed at doublets and segmentation merges takes the cell type the analysis exists to find. Turn it on per sample only if a section genuinely needs it. Choose all three by reading `qc_report`'s retention curves — that deck exists for this decision and nothing else consumes it.

**`min_cells` masks rather than removes.** It writes `var["passes_min_cells"]` and gates HVG *candidacy*; the genes stay in the object with their `counts` and `lognorm` layers. Removing them was actively harmful on a targeted panel, because a gene specific to a rare population is by definition detected in few cells: at `min_cells=100` on a 32k-cell test ROI, a hard filter deleted 14 of 32 oocyte markers (FIGLA, ZP4, LHX8, NLRP5…), 7 of 37 granulosa (AMH, FST, GREM1, IHH) and 4 of 19 theca (CYP17A1, INSL3) — the canonical markers for the very cell types `sample_summary` exists to identify. Masking costs nothing measurable: depth correlation was unchanged or slightly better (0.510/0.282 vs 0.532/0.311), the resolution sweep tracked the hard-filter version within 2 clusters at every step with identical endpoints, and the annotation structure was preserved one resolution step later. It is not a *no-op*, though: `seurat_v3` fits its mean-variance trend across whichever genes are present, so keeping the extra 1,914 shifts that curve and reshuffles the top 2000 — 1,941 of 2,000 shared, 59 swapped, all of them passing `min_cells`. Reading the sweep fresh after this change is therefore necessary; a resolution does not mean the same thing across it.

**Normalization deliberately takes no `target_sum`**, so scanpy's default applies: the median pre-normalization cell total. That is principled here rather than arbitrary. A fixed target far from the data's own scale — CP10K against a ~200-transcript median — multiplies every cell by a factor inversely proportional to its depth, and because `log1p` follows, that factor leaks back into the values. Measured on both test ROIs, CP10K drove PC1's correlation with depth to **0.97** (from 0.31–0.53), lost one sample's immune cluster entirely, and halved every reference-correlation margin (endothelial 0.457 → 0.168). The cost is that `layers["lognorm"]` is on a per-sample scale (226 and 198 on the two test ROIs) and so is not comparable across samples or against an external atlas — anything needing that normalizes to CP10K itself from `layers["counts"]`, as `sample_summary`'s centroids do.

The cut is resolved **per sample**, most specific source winning: an optional `min_counts` / `min_cells` / `max_counts_quantile` **column on the samplesheet**, else the cohort-wide `--min_counts` / `--min_cells` param, else the script's default. So a cohort where one sample needs a harsher cut is one edited cell, not a separate run, and the samplesheet records which sample got which value. `main.nf`'s `resolveThreshold()` is the single definition of that precedence. Because the cut varies across the channel it rides in the **input tuple**, while `resolutions` (and `chunk_size` / `n_top_genes`) stay plain `val`s — the sweep is cohort-wide by design, since comparing the same resolutions across samples is what `cluster_report` is for. Note that per-sample cuts mean the cohort is **not** uniformly filtered, so a cluster that is thin in one sample may reflect a harsher threshold rather than biology.

Three wiring details. An empty or whitespace-only cell counts as **absent**, so a column filled in for only some samples falls back per row instead of passing an empty flag. `0` does **not** count as absent, and both `resolveThreshold`'s param arm and the modules' guards avoid Groovy truthiness (`!= null` and `!= ''`, not `?:`) for that reason — zero is a meaningful threshold (keep every cell) that a truthy test would silently collapse back to the default, so asking for no filtering would quietly filter. And `cluster_sdata_gpu_ooc` applies the same numbers as a boolean mask over `obs["total_counts"]` / `var["n_cells_by_counts"]` rather than through `filter_cells`/`filter_genes`, since filtering through views is incompatible with Dask-backed X — the flags mean the same thing but reach the data by a different route.
- `cluster_sdata_gpu_ooc` — same clustering pipeline as `cluster_sdata_gpu`, but streams the table's X matrix through Dask (rapids-singlecell out-of-core) so tables too large for VRAM (e.g. a merged cohort from `concat_sdata`) can still run on a single GPU. All three steps now select 2000 HVGs as part of the shared recipe, so `--n_top_genes` no longer switches HVG on — it **hard-subsets** to a different count, dropping the other genes from the output entirely rather than merely flagging. It stays off by default because that would cluster a different feature space than the other two steps; turn it on only if the materialized X does not fit. Note the chunked PCA differs from the in-memory one at ~1e-5, which is enough for Leiden to land ±1 cluster either way versus `cluster_sdata_gpu` — the embeddings themselves correlate at 1.000000
- `create_centroids` — reduces each clustered zarr to a per-group centroid store, `<sample>_centroids.h5ad`. This is the artifact boundary the report decks read across, so they never open a counts matrix: 1.1 GB of clustered zarr against 6.5 MB of centroids on a test ROI, and `sample_summary` was re-reading all of it every render to recompute the same numbers. Per-sample fan-out, publishing a three-column handoff sheet (`sample,path,centroid_path`) because the decks need both artifacts — the centroids for expression, the clustered zarr for `obs`, `obsm` and the spatial elements its tissue slides draw.
    - **Everything is stored as SUMS over a group's cells, never means**, because sums are additive: the profile of any union of groups — across resolutions, across samples, a consensus cluster — is the plain row-wise sum of its members, and `n_cells` sums with it. A mean would have to be un-averaged (weight by n) before it could be combined, the same number by a longer route. Two layers, because neither is recoverable from the other: `X` is `cp10k_sum` (per-cell CP10K normalization, THEN summed) and `layers["counts"]` is `counts_sum` (raw counts summed). The centroid a deck correlates against a reference is `log1p(cp10k_sum / n_cells)` — mean-of-normalized, matching Seurat's `AverageExpression` and therefore the published centroid tables in `assets/`. Summing raw counts instead lets deep cells dominate in proportion to depth, which on ovary is not marginal: oocytes carry ~5,000 transcripts against a ~200 median. The counts layer is kept for DE input, where edgeR/DESeq2 estimate size factors themselves, and it is **not** derivable from the CP10K route — that one needs each cell's library size, which summing raw counts discards
    - **CP10K rather than the pipeline's own normalization**, deliberately. `cluster_sdata`'s `normalize_total` takes no `target_sum`, so `layers["lognorm"]` is on each sample's own median scale (226 and 198 on the two test ROIs) and is comparable neither across samples nor against an external atlas. These centroids exist to be compared, so they are built from `layers["counts"]` and normalized here. Not `expm1(X)`, which would round-trip a log transform through a matrix `scale` has already overwritten
    - **`cluster_v1` is computed here, and that is a move.** It is the size ranking — 1 is the sample's largest cluster at that resolution — and `sample_summary` used to derive it at render time, inside the same cell that built the centroids. Splitting the centroids out without the ranking would leave the deck re-deriving a key it then has to join the centroids on, which is two definitions of one id. **The deck joins on this column; it does not recompute it.** The second numbering, v2 (clusters renumbered down their own centroid-correlation dendrogram so adjacent numbers are transcriptionally adjacent), stays at render time: its recipe is unsettled — which genes, which linkage — and stored here, every trial of it would cost a cohort-wide re-run and renumber every heatmap in every deck
    - **The obs schema is the same whatever the grouping**: `grouping` (the obs column summed over), `group` (its value), `n_cells`, plus `sample`. Rows from a `leiden_res_<r>` column carry `resolution` and `cluster_v1` as well, because a resolution is a number the decks select on and `"0.60"` is not recoverable from `"leiden_res_0.60"` without parsing. That is decided by the **column name**, not by which mode produced it, so `--group_by leiden_res_0.60` yields exactly the sweep's rows for that resolution — verified identical in obs, `X` and `counts`. The identity columns are pinned to `pd.Categorical` explicitly rather than left to fall out of the data: both anndata's writer and `ad.concat` convert object string columns only when cardinality makes it pay off, so `group` and `cluster_v1` came back categorical from a sweep store (77 rows, 7 unique at one resolution) and object from a single-resolution one (7 rows, 7 unique) — same values, different dtype, decided by how many resolutions were run
    - Centroids are computed at **every resolution in the sweep**, not just the one in `assets/chosen_resolutions.csv`. That file is a curated judgment made by reading `cluster_report` and it stays a report-level knob: revising a sample's chosen resolution re-renders a deck, it does not re-run this step. Restricting here would also make this the first `bin/` script to read a curated file, which the compute/report split avoids — and the same rule is why `--group_by` names a column already in `obs` rather than reading a label file
    - **`--group_by` is not for coarsenings.** Sums are additive, so a cell type defined per cluster, a consensus cluster, or any other union of clusters is the row-wise sum of its members' rows in the default store — the deck adds them. It earns its cost only when the grouping **splits** a cluster, which is the per-cell case. A `--group_by` run writes `<sample>_centroids_<column>.h5ad`, so it never displaces the sweep store
    - Deliberately its own step rather than folded into `cluster_sdata`, which already holds the matrix in memory: Nextflow hashes the task script, so folding it in would make any change to the centroid recipe re-run PCA, UMAP and the whole Leiden sweep for the cohort
- `cluster_report` — renders `cluster_report.qmd` into one cohort-level pptx deck over every clustered zarr. Unlike the other notebook step it takes **no params**: every zarr is staged flat into the work dir and the notebook globs `*.zarr`, so staging is the whole input contract and there is no registry entry. Two details are easy to trip over: the zarrs must be staged under indexed names (`stageAs: 'sample*.zarr'`) because `cluster_sdata*` publishes every sample's output as `clustered.zarr` and a flat fan-in would be a name collision; and the qmd must pin `jupyter: python_spatial`, since Apptainer bind-mounts `$HOME` and a stray `~/.local` kernelspec otherwise shadows the container's, failing every import while still exiting 0 under `error: true`. Per sample it emits QC-on-UMAP, the resolution sweep on UMAP, the same sweep in tissue coordinates (both split across `CLUSTER_SLIDES` slides, so slide n of one holds the same resolutions as slide n of the other), and a full-slide tissue plot at `SPATIAL_RESOLUTION`. Marker size is derived from each axes' area and the cell count rather than fixed — one constant cannot serve both a five-panel sweep and a full-slide plot, nor a sparse strip and a dense section. Cluster colours come from tab10 below 11 clusters and tab20 above: tab20 is ten dark/light pairs, so the 2-cluster panels the low resolutions produce would be navy against pale blue
- `qc_report` — renders `qc_report.qmd` into one cohort-level pptx deck over every **raw `create_sdata` zarr**, to be read *before* clustering so the filtering thresholds are chosen from the data. Same staging-is-the-contract fan-in as `cluster_report` (indexed `stageAs`, glob `*.zarr`, no params, no registry entry, pinned `jupyter: python_spatial`), and the same `error: true` caveat — read the slides, not the exit status. Three things are specific to it:
    - **It never reads a value out of X.** Every metric it shows is already in `obs` from `create_sdata`, so the table is loaded with `ad.experimental.read_lazy` and X stays a Dask array whose graph is never computed. This is the payoff `create_sdata` was annotating QC metrics for. The one wrinkle: `read_lazy` returns `obs`/`var` as xarray `Dataset2D`, which anndata's own `strings_to_categoricals` chokes on (`unhashable type: 'DataArray'`) — and every `sc.pl`/`sq.pl` call sanitizes first, so both `to_memory()` lines in the loader are load-bearing. That is a [known anndata limitation](https://github.com/scverse/anndata/issues/981), not a quirk of this deck, and is expected to go away
    - **It must run on `create_sdata` output, not `cluster_sdata`'s.** Clustered zarrs have already had the `min_counts` cut applied, so the discarded tail is gone and the distributions look clean no matter how much was thrown away
    - **It derives nothing, and has no fallbacks.** Every obs column it reads is listed in `REQUIRED_OBS` and checked up front in the per-sample loop, so a zarr predating a column fails on the first sample with that column named rather than several slides later. A fallback derivation would be a second definition of the metric, letting a stale cohort render a deck whose numbers came from outside the pipeline — re-run `create_sdata` instead

    **The deck's job is to choose the cell and gene filtering thresholds `cluster_sdata*` applies** (`min_counts`, `min_cells`), and what it renders is scoped to that. It began as an exploratory surface showing every metric on every plot type — 46 slides per sample, ~15 min, ~73 MB — and has since been cut back on measured redundancy rather than taste; see the histogram and scatter notes below for the evidence. It now renders 21 slides in ~30 s.

    **`SECTIONS` is the switch.** A set of section names near the top; comment a line out to drop that section and nothing else needs touching. Enabled by default are `cell_distributions` and `gene_distributions` — the two a cut is actually read off — plus `cell_scatter`. Disabled: `transcript_stats`, `cell_tissue`, `molecule_maps`. The split matters because **cost tracks rasterisation, not slide count**: 26 matplotlib scatter slides cost ~7 s, while the 4 datashader molecule maps and 14 rasterised tissue panels are essentially the entire render time (~40 s versus ~15 min). Nothing is deleted when a section is off — every slide function and metric list stays, just unassembled.

    Three sections per sample, **cells → genes → transcripts**, widest unit to narrowest, so each is a finer-grained account of the same sample rather than an unrelated appendix.

    `METRICS` entries are `(obs column, axis label, scale)`, and the **scale is what lets one list drive three plot types** — it picks the histogram's binning and axis and the tissue panel's colour norm, which are the same decision asked twice. Four kinds, and they are not interchangeable: `log` (counts and areas spanning decades; zeros cannot be drawn and are counted), `linear` (bounded ratios and percentages; zeros are **kept**, since `pct_control` is 0 for 87% of cells and the log panels' zero-dropping would empty the panel), `count` (small integers binned on half-offset integer edges — `nucleus_count` takes four distinct values, where 60 logspace bins are 56 empty bars), and `categorical` (no bins and no colourbar at all — a horizontal bar chart of category counts, and a discrete palette with a legend in tissue). Getting the norm wrong is not cosmetic: a log norm over `pct_control` (0–3%) or `nucleus_ratio` (0–1) spends the whole ramp below 1 and masks every cell at 0, so the panel reads as empty tissue.

    **Histograms and scatter colours are curated, and the cuts are measured.** A histogram here is a threshold tool, so a metric earns one only if it *is* a cut or says whether a cut is the right instrument; a scatter colour earns a slide only if it adds a dimension the two axes do not already carry. `METRICS` still holds all fourteen and still drives the tissue section — only the histogram and scatter lists were shortened.
    - `CELL_HIST_METRICS` — four panels: `transcript_counts` and `n_genes_by_transcripts` (the columns `cluster_sdata*` filters on), plus `cell_area`/`nucleus_area`, which are not thresholds anyone sets but are there because if segmentation is broken a count cut is the wrong instrument, and that must be visible beside the counts.
    - `GENE_HIST_METRICS` — two, not the four `create_sdata` writes, because the other two are the same variables rescaled (**verified exactly, not approximately**): `pct_dropout_by_transcripts == 100 * (1 - n_cells_by_transcripts / n_obs)` and `mean_transcripts == total_transcripts / n_obs`. Plotting both members of a pair draws one distribution twice.
    - `SCATTER_METRICS` — four of fourteen, chosen by the R² of predicting the colour from log(transcripts) and log(genes), i.e. how much of it is position restated. Kept: `pct_control` (0.004), `nucleus_ratio` (0.20), `nucleus_area` (0.53), `cell_area` (0.60). Dropped: the two columns that **are** the axes; `transcripts_per_gene` (0.957, and exactly `transcript_counts / n_genes_by_transcripts`, so on log axes it is distance from the diagonal); all four `pct_transcripts_in_top_*` (0.75-0.89, rising with k, and mutually r = 0.72-0.96); `nucleus_count` (99.4% of cells share one value, so a continuous ramp is one colour); and `control_counts` (87% zeros over 14 discrete values, same signal as `pct_control`).
    - Scatter colours carry a **`vmax` clip** where the metric has a long tail — `cell_area` 150 and `pct_control` 1.0, both the 99th percentile rounded, fixed rather than per-sample so a colour means the same value across a cohort. `sc.pl.scatter` has **no `vmin`/`vmax`** (checked against the installed scanpy), so the clip is set afterwards with `set_clim` on the `PathCollection` it leaves on the axes; the colourbar follows because it was built from that mappable.

    Histograms stay gridded in 2x2s of `HIST_PANELS` because the metrics are small multiples of one measurement, where the tissue and scatter slides are one figure each. Leftover axes are `delaxes`'d rather than hidden — a hidden axes still reserves its cell under `tight_layout` — and `tight_layout` then repacks the survivors, so the two-panel gene slide fills the slide rather than sitting in the top half.

    **`codeword_category` is carried across sections as colour**, and is **read from `var`**, where `create_sdata` annotates it (see its note above for why a one-to-one lookup is safe to compute there). The deck used to rebuild it from the molecule table itself, and that was its last reason to materialize points on a default render; it now derives nothing on the gene axis either. It is normalised to object dtype with `None` **on the way in** rather than trusted — a zarr round-trip can return the column as a categorical or a nullable string, and `pd.NA == "predesigned_gene"` is `pd.NA` rather than `False`, so every comparison-built mask would raise `boolean value of NA is ambiguous`. That is a dtype normalisation, not a second definition: an unmapped gene stays unmapped and the slides name it. On the gene axis it resolves to predesigned vs custom panel probes, the question the histograms cannot answer: whether separately-designed custom probes land in the same abundance-detection cloud as the catalogue ones. Consequences worth knowing:
    - The molecule table is therefore loaded **only for the sections that plot it** (`transcript_stats`, `molecule_maps`), and a default render — where both are off — never touches `points` at all. `TX_COLUMNS` drops `feature_name` with the lookup, since that column existed only to build it. The gene slides no longer depend on the load at all, so its failure costs only the molecule slides.
    - `CATEGORY_INK` fixes one colour per category deck-wide, so a category keeps its colour between the gene scatter, the rank curve and the qv distributions, which are read against each other. Hue families carry the meaning: real genes blue/orange, every control and unassigned class red/purple/amber.
    - Reindexing leaves **`pd.NA`** for a gene with no transcript anywhere in the sample. `codeword_category` is pandas `string` dtype, so `pd.NA == "predesigned_gene"` evaluates to `pd.NA`, not `False`, and every comparison-built mask raises `boolean value of NA is ambiguous`. The lookup is normalised to object dtype with `None` **once, where it is built** — do not re-introduce the string dtype downstream. The unmapped state is real (absent even before cell assignment) and is named on the slides, not dropped.
    - The minority class is drawn **last and larger** on the scatter; at 100 in 5,101 plotted in index order it is buried and the slide shows nothing. The rank curve stays one colour and marks only the minority categories on it — marking 4,995 of 5,101 would redraw the line in a second colour and say nothing.

    The **gene section** reads `var`, which `create_sdata` annotated at the same point it annotated `obs`, so it derives nothing either. `GENE_METRICS` reuses the same `(column, label, scale)` shape and the same histogram function via its `level="var"` argument — the two populations are the same figure over a different frame, so writing them twice would only let them drift. `pct_dropout_by_transcripts` is the one linear entry: it is a bounded percentage running to 100 for the genes no cell detected, which a log axis drops entirely, and those are the genes worth finding. Beyond the histograms: a rank-abundance curve (rank linear, abundance log; zero-detection genes marked as a band at the foot rather than silently ending the curve early), an abundance-vs-detection scatter that separates "not expressed here" from "many transcripts in few cells", and a slide **naming** the undetected genes. That last one is the only list in the deck rather than a figure, because the useful output is which probes to look at and a name cannot be read off a distribution. On a test ROI it surfaces 30 of 5,101, and they are the expected absent-tissue markers for the section (Y-chromosome genes, eye, kidney, adrenal) — which is why the slide names them rather than calling them failures.

    The **transcript section** is the deck's **one deliberate exception to "derives nothing"**, and the notebook says so where the rule is stated. `qv`, field of view and nucleus placement are properties of the molecule table, not summaries of X, so `create_sdata` never computed them and there is no pipeline definition for this deck to contradict — the rule exists to stop two definitions of one metric, and here there is only one. The exception has already shrunk once this way: codeword category used to be on this list and is now read from `var`, because a strictly one-to-one lookup has a natural home on the gene axis. If any of the remainder earns a place in `create_sdata`, the deck should read it from there and the exception should shrink again — note `uns` is **not** that home, since `anndata.concat` drops it (`uns_merge` defaults to `None`, and `concat_sdata` does not pass it), exactly as it drops `var` columns. Mechanically: `read_zarr` now takes `points` too (lazy Dask, free until asked), and `TX_COLUMNS` is materialized **once per sample** — never the whole frame, since coordinates and ids are most of its width. ~7M rows for a 21k-cell ROI takes about a second. This is the deck's only shared derived state, so it gets **its own `try`** rather than relying on the per-slide catch: if it fails, all four molecule slides are meaningless and are skipped together. A whole-slide sample is where it becomes the binding constraint, and the fix there is lazy Dask aggregation (`value_counts` and `groupby` both support it), not materialize-and-subsample. Four slides: the `qv` distribution with `QV_THRESHOLD` (20, Xenium's own default) drawn but **never applied by the deck** — because Xenium already applied it: `transcript_counts` is built only from molecules at `qv >= 20` (see the `create_sdata` note above for the verification), so the fraction below threshold is **data discarded before counting**, not a marginal tail inside the counts. That is what earns the slide its place — a sample that lost 30% of its molecules here looks sparse on every per-cell distribution for a reason that is not biological, and nothing else reports it; the **qv distribution per category**, each normalised to its own share so 162 negative-control probes are as readable as 5.4M genes — the control check the deck exists to make, since a negative control scoring like a real gene means the decoder cannot tell them apart and no per-cell metric would reveal it (on a test ROI: genes at median 40, `deprecated_codeword` 17, `negative_control_codeword` 10.5, `negative_control_probe` **0.0** with 96% below threshold), with the medians restated as a table under its **own explicit heading** because pandoc puts a table on a fresh slide regardless and it would otherwise arrive untitled; the codeword-category breakdown on a log axis (the categories span five decades, so on a linear axis every control bar is invisible, which is the opposite of what a control is for); per-FOV yield and median qv sharing a field order, the only view here that can see an *instrument* problem rather than a biological one, since a bad field's cells just look like poor cells in every per-cell distribution; and transcript placement (z, nucleus distance, nucleus overlap).

    **Molecule maps are the deck's only spatial view not conditioned on segmentation**, and that is their reason to exist: every tissue slide above is drawn from cells, so a molecule assigned to no cell is invisible there. They are drawn entirely by `spatialdata_plot.render_points`, not hand-rolled — an earlier version binned and KDE-smoothed the points itself and was replaced. `TX_MAPS` lists four: the whole table, below qv, assigned to no cell, and control-or-unassigned codeword. On a test ROI the third is **5.3% of all transcripts**, a segmentation number nothing else in the pipeline reports, and it traces rings around antral follicles plus a band at the tissue edge.
    - **Each map states its subset's size and share** as text, from one `dask.compute` over all four at assembly. The maps answer *where*, not *how much* — a clipped count map is deliberately close to presence/absence, so magnitude cannot be read off the colour — and the share assigned to no cell is the one segmentation figure nothing else in the pipeline reports (5.3% on a test ROI). It was previously available only by eye.
    - **Counts, not fractions.** A fraction answers "what share here", a magnitude question; these slides are read for **location**. A count map at a low `vmax` is close to presence/absence, which is the encoding location wants, and it sidesteps the fraction map's worst artefact where a canvas point holding one flagged molecule reads as 100%.
    - Each subset is a **separate registered points element**, not a colour argument, so all four are the identical call. Filtering a points element preserves its transformations in `.attrs` — they must **not** also be passed to `PointsModel.parse`, which raises `Transformations are both specified for the element and also passed as an argument`.
    - **`density=True` never builds a colourbar** (verified: single axes in every mode, including `colorbar=True`) because plain density routes to the categorical shader. So the maps colour by a **constant column reduced by `count`**, which reaches the continuous shader and does build one. Delete `MAP_COUNT_COLUMN` the day that changes.
    - **`size` is not a marker size** on the datashader path — it is the only handle on spreading, `round(sqrt(size) * dpi/100)` canvas points. `MAP_POINT_SIZE = 0.01` gives 0 (no dilation) at 400 dpi. The control subset is two orders of magnitude sparser than the others and would be invisible without dilation, so it alone uses `MAP_SPARSE_POINT_SIZE`.
    - **`Greys`, deliberately, not the deck's `viridis`.** These are read for structure; fine spatial detail is carried almost entirely by luminance (the chromatic channels have ~a third the acuity), so a ramp's usable structural contrast is its lightness range, and white-to-black is the widest. Extra hues buy discrimination of *values*, which these slides do not ask. White at the bottom is load-bearing: a count of 0 **is** an empty canvas point.
    - `vmax` is a **clip and per-map** (4 for the whole table, 1-2 for the sparse three). It is tied to `FIGSIZE` and 400 dpi, because the datashader canvas is figure-inches x dpi — the same data topped out at 32-41 counts per point in a 20in/100dpi test figure and 77-105 in a 9in/100dpi one. **Re-tune by rendering, not by scaling arithmetic.**
    - The canvas cell (~0.56 µm) is **smaller than the mean spacing between molecules** (~4.9/µm², so ~1.5 per point), and there is no minimum-count guard because datashader offers none. That is a sampling property, not a colour-scale one — clipping hides it rather than fixing it.
    - `fit_tissue_panel` is shared with the label-based tissue slides; the `tight_layout` trap above applies identically here, since `fig.colorbar` attaches the same kind of free-standing axes.

    Two details on the cell histograms are worth keeping straight. Cells fall off a **log** panel two ways and are counted separately: a **zero** cannot be drawn, and a value that was **never measured** is NaN — the reader leaves `nucleus_area` NaN, not 0, for a cell segmented without a nucleus (70 of 21,724 on one ROI, matching `nucleus_count == 0`), and `create_sdata`'s division carries that NaN into `nucleus_ratio`. Folding those together, or filtering non-finite values before counting, silently loses exactly the cells a QC deck exists to surface. Plotting an unmeasured cell at 0 would file it among genuinely cytoplasm-heavy ones.

    The tissue slide uses **`spatialdata_plot`'s `render_labels`**, not a scatter, so each cell is painted at its own segmented footprint. That is what retires the marker-size question — no constant travels between a 2,000 µm ROI and a whole slide, and deriving one from cell spacing still leaves a coverage factor that is pure taste. `render_labels` rather than `render_shapes` because the table annotates `cell_labels`, so it needs no schema change, while colouring `cell_boundaries` would need a second table keyed on `cell_id`; at this magnification a cell is ~2 pt across, so the polygons' extra fidelity is invisible anyway. Four traps here:
    - **`LogNorm` fails** (`spatialdata_plot` calls `norm.autoscale_None` on the 2D label array and matplotlib 3.11's generated `LogNorm` transforms it unconditionally), hence the `SafeLogNorm` shim — delete it when the libraries agree
    - spatialdata's `global` frame for a Xenium read is in **pixels**, so the axes are tick-less rather than mislabelled as µm, and the squidpy version's scale bar is gone with it
    - the slide is called **once per metric**, so each gets its own norm and colourbar; sharing a scale is not an option even in principle when genes top out near 2,400 against ~10,600 transcripts and 3% control
    - **never call `tight_layout` on this figure.** `spatialdata_plot` attaches its colourbar as a free-standing axes that `tight_layout` does not know about, so it expands the main axes from 77% to 92% of the figure width — straight under the colourbar — and the equal-aspect axes then centres itself in the oversized box, leaving a band of empty slide on its left. The panel is positioned by hand instead, fitted to the tissue's own aspect (read back from the drawn limits) and touching whichever edge of the slide binds first, with the colourbar re-seated beside it. These ROIs run both ways — one a 3:1 strip, the other a 1:2.2 block — so the binding edge differs per sample
- `sample_summary` — renders `sample_summary.qmd` into one cohort-level pptx deck over every **clustered zarr paired with its `create_centroids` store**, and is where a cluster becomes a cell type. It **no longer reads `layers["counts"]` or aggregates over it** — every per-cluster centroid comes from the store instead, which is what the counts layer was being read for. It still reads `layers["lognorm"]` for the two per-cell marker slides (`marker_dotplot`, `marker_umaps`); those are per-cell views the centroid store cannot supply, so the deck is not matrix-free, it just no longer carries a second copy of the matrix or re-derives cluster means from it. So it takes a `create_centroids` handoff sheet (`sample,path,centroid_path`), not a `cluster_sdata*` one — a sheet without `centroid_path` fails with a message saying so. Two consequences worth knowing. **`cluster_v1` is joined, not derived**: the store ranks clusters by cell count at every resolution, and the deck maps the store's `group` labels onto `obs` rather than re-running `value_counts`, so there is one definition of the id the centroids are keyed on. **The centroid is one division**: the store holds summed CP10K, so `log1p(X / n_cells)` is the same mean-then-log atlas pseudobulk the deck used to compute itself — verified bit-for-bit, the repoint reproduces the previous deck exactly (all 28 figures identical by md5, all slide XML identical, `cluster_annotations.csv` and `cell_type_composition.csv` identical). v2 (the dendrogram renumbering) stays at render time; see `create_centroids` for why. Same staging-is-the-contract fan-in as the other two decks, but unlike them it takes **params**: `--chosen_resolutions` (which resolution of the sweep each sample is reported at), `--follicle_markers` and `--reference_major` (the tissue-specific assets), `--cell_type_annotations` (the hand-made calls), and `--curated_oocytes` (the zoom targets). All are defaulted in `nextflow.config` and staged under fixed names, so the notebook reads a name rather than a path.
    - **Two evidence families, one assignment rule.** Marker-set means name the follicle types the reference does not contain (granulosa, oocyte, theca, from Sci Adv adm7506 Data S5 at quality score 1); Spearman correlation of each cluster's centroid against the reference's four major types names the rest (Endothelial, Immune, Pericyte, Stromal, from Data S6). Both are concatenated into one clusters x cell-type frame and assigned by the **argmax down each COLUMN** — down the column asks "which cluster is most Endothelial", where across the row asks "which of the four is this cluster most like" and answers Stromal nearly everywhere in stroma-dominated tissue.
    - **A cluster answers for at most one cell type.** Where two types' argmax lands on the same cluster the conflict is resolved greedily by strength of claim — each type's lead over its own runner-up, on that column's own 0-1 scale so a marker mean and a correlation compare — and a type whose best cluster is taken falls through to its next best. Joined `granulosa + oocyte` labels are gone: they cannot be a composition column, and counting a cluster under two types double counts its cells. **The practical consequence is to over-cluster rather than under-cluster**: one type over many clusters is fixable in the sheet with a row each, while two types merged into one cluster is not fixable at all, since no sheet edit separates cells that are genuinely mixed.
    - **The correlation runs over every gene the sample and the reference share**, with no selection. A set drawn from the paper's own type-specific table (Data S8) was built and measured first and is better on both metrics that matter — mean margin 0.23-0.25 against 0.096-0.099, and all four types landing on four different clusters rather than three — but the intersection won on being simple: no parameter, no asset, no selection rule to defend. The measurement is recorded in the notebook where `REFERENCE` is loaded.
    - **Centroids are CP10K, not the pipeline's own scale.** Counts, each cell normalized to 10,000, averaged over the cluster, then `log1p` — in that order, since averaging logs is a different quantity. `layers["lognorm"]` cannot be used: `cluster_sdata` takes no `target_sum`, so its scale is the sample's own median and is not comparable against an external reference. Spearman ranks genes within a profile, so the choice does not affect the correlation at all — it is the marker-set heatmap, which prints its values, that needs a fixed scale.
    - **`cell_type_annotations.csv` is the override, and it wins.** One row per (sample, cell_type, cluster): several rows give one type several clusters, and a row with a **blank** cluster means "judged not present in this sample", which is how a call is overridden downward — the argmax always exists, so without it a type could never be dismissed. Hand calls are placed first and the clusters they name are withheld from the greedy pass. The deck emits `cluster_annotations.csv` with the argmax already filled in, so curating a cohort is editing rather than authoring.
    - **Two switches, both currently OFF.** `SHOW_SCALEBAR` — boxed, the bar hid tissue; boxless it stayed unreadable, a 25 µm bar being about the size of the cells beneath it. `SHOW_OOCYTE_ZOOMS` — the zoom section is a crop, an H&E read and a points materialization per stage per sample, two thirds of the deck's weight (26 MB to 7.6 MB, 47 slides to 34), so it is off while the rest is iterated on. **Turn it back on for a real cohort render**; the zooms are the only slides at a magnification where a call can be checked against a follicle.
    - Three spatialdata_plot behaviours cost a render each and are commented where they bite: filtering a **points** element **drops its transformations** (shapes keep theirs, so the marker element goes back through `PointsModel.parse` with the parent's transform passed explicitly); `render_points` accepts `palette=` and **ignores** it, so colours are set on the artist after `show` — and every point lives in ONE `PathCollection` with a per-point colour array, so they go on in row order; and clearing a scatter's edge colour **halves the visible dot size**, since matplotlib strokes each dot in its own colour at linewidth 1.
- `concat_sdata` — merges multiple sample zarrs into one
- `downsample_sdata` — subsamples cells from a SpatialData zarr
- `plot_follicle` — renders the `plot_follicle.qmd` Quarto notebook per follicle zarr

nextflow run main.nf --step downsample_xenium_region --samplesheet assets/samplesheet.csv
nextflow run main.nf --step create_sdata --samplesheet assets/downsampled_region_samplesheet.csv
nextflow run main.nf --step create_adata --samplesheet assets/r21_adata_oscer_samplesheet.csv
nextflow run main.nf --step create_follicle_sdata --samplesheet my_sample_zarrs.csv --cell_ids_file assets/stage_quality_area_all_rois.csv

nextflow run main.nf --step cluster_sdata --samplesheet my_sample_zarrs.csv --resolutions 0.5,1.0,1.5
nextflow run main.nf --step cluster_sdata --samplesheet my_sample_zarrs.csv --min_counts 25 --min_cells 3 --max_counts_quantile 0.99
# per-sample cut: add min_counts/min_cells columns to the samplesheet; blank cells
# fall back to the --min_counts/--min_cells params, then to the script defaults
nextflow run main.nf --step cluster_sdata --samplesheet my_sample_zarrs_with_cuts.csv

nextflow run main.nf --step create_centroids --samplesheet results/cluster_sdata_samplesheet.csv
nextflow run main.nf --step create_centroids --samplesheet results/cluster_sdata_samplesheet.csv --group_by cell_type
nextflow run main.nf --step cluster_report --samplesheet results/cluster_sdata_samplesheet.csv
nextflow run main.nf --step qc_report --samplesheet results/create_sdata_samplesheet.csv

`my_sample_zarrs.csv` above is a stand-in for a `sample,path` CSV pointing at a prior step's output zarrs (e.g. `results/<sample>/create_sdata/<sample>.zarr`). Some producing steps now publish a ready-to-use handoff samplesheet next to their outputs (`<outdir>/create_sdata_samplesheet.csv`, `<outdir>/cluster_sdata_samplesheet.csv`) that you can point the next step's `--samplesheet` straight at; for steps without one yet, hand-build the CSV.

`downsample_xenium_region` requires the samplesheet to include `xmin,ymin,xmax,ymax` columns (µm coordinates) and an optional `region_name` column, which defaults to the sample ID if omitted. `downsample_sdata` requires `--fraction` or `--n_cells`.

### Profiles
Defined in `nextflow.config`:

| Profile | Executor | Container |
|---------|----------|-----------|
| (none)  | local, no container | requires activated conda env with Quarto + notebook deps |
| `local` | local, Apptainer | `babiddy755/python_spatial:1.2.0`, 8 CPUs, 16 GB |
| `oscer` | SLURM on OSCER HPC, Apptainer | same image, 16 CPUs, memory retries 48→96→144 GB; GPU steps use the `sooner_gpu_test_h100` partition with `--gres=gpu:1 --nv` |

**Run directories.** The `local` and `oscer` profiles set their own `workDir` and `outdir` so nothing lands in the repo (runs are typically launched from the repo root). Each run gets one self-contained directory, `<out_root>/<run_id>/{work,results}`, so a whole run is a single unit to size (`du -sh`) or prune (`rm -rf`). The shared Apptainer cache is a sibling of the run dirs (`<out_root>/apptainer_cache`), never nested under a `run_id`, so it survives across runs:

- `local` → `~/xenium_nb_out/<run_id>/{work,results}`
- `oscer` → `/scratch/$USER/xenium_nb_out/<run_id>/{work,results}`

Keeping `work` and `results` under the same root also keeps them on one filesystem, which the modules' hardlink publishing (`mode: 'link'`) relies on to avoid a second full copy of each zarr.

Both profiles set `cleanup = true`, so the work dir is deleted once the whole run **completes successfully** — leaving only the (hardlinked) results, i.e. each output stored exactly once. Nextflow scopes cleanup to success: a **failed** run keeps its work dir, so resume-after-failure (bump resources, skip the samples that already finished) still works. What cleanup forfeits is resume-*from*-success — reusing a finished run's cache on a later relaunch — which this single-process-per-step pipeline (no DAG to reuse) rarely needs.

Because `run_id` defaults to a fresh timestamp, `-resume` across separate launches only works if you pin the id with `--run_id <name>` (or recover the prior timestamp from the run dir name / `.nextflow.log` and pass it back). `-resume` must also be run from the same launch directory, since its cache lives in `.nextflow/` there. Note `cleanup = true` deletes that cache on success, so resume is available only after a failure.

The `local` profile defaults `samplesheet` and `cell_ids_file` to the test assets, and also points `cluster_sdata_gpu` / `cluster_sdata_gpu_ooc` at the local RAPIDS container with WSL2 GPU passthrough settings:

```bash
nextflow run main.nf --step cluster_sdata_gpu -profile local
nextflow run main.nf --step cluster_sdata_gpu_ooc -profile local
```

`cluster_sdata_gpu_ooc` additionally needs `dask` and `zarr` in the container — both are present in `babiddy755/python_spatial:1.2.0` as rapids-singlecell/spatialdata dependencies (verified).

## Architecture

### Single entry point, one workflow per step
`main.nf` dispatches on `--step` to one of fourteen named workflows, each of which reads a samplesheet, builds a channel of tuples, and pipes it into a single process. There is no chaining between steps inside Nextflow — to run steps in sequence, point the next step's `--samplesheet` at a CSV listing the prior step's published output paths (e.g. `results/<sample>/create_sdata/<sample>.zarr`). As a convenience (not a control-flow link), every artifact-producing step publishes a handoff samplesheet into `outdir` (`<step>_samplesheet.csv`) that you can feed directly to the next step. Each process emits a `samplesheet_row` output whose published path comes from a per-module helper that also drives that module's `publishDir` — so the convention is single-sourced in the module and `main.nf` just `.map { it.text }` + `collectFile`s the rows (the `.text` read makes `collectFile`'s `sort` deterministic). The row fragment is kept out of the publish dir via `publishDir`'s `saveAs`. Schemas: the single-per-sample producers (`create_sdata`, `create_adata`, `cluster_sdata`, `cluster_sdata_gpu`, `cluster_sdata_gpu_ooc`, `downsample_sdata`) and `concat_sdata` emit `sample,path`; `create_follicle_sdata` emits `sample,cell,path` (one row per per-cell zarr) for `plot_follicle`. `concat_sdata` and `create_follicle_sdata` also stage `.zarr` inputs into the work dir, so their row generation globs `*.zarr` and excludes the staged inputs.

### Create/cluster/downsample scripts (`bin/`)
Every step except `plot_follicle` runs a plain Python script with an `argparse` CLI (`bin/<step>.py`), invoked directly from its module's `script:` block — no params YAML involved.

### Notebook registry (`assets/notebook_registry.json`)
Maps analysis notebook IDs (currently just `plot_follicle`) to their `.qmd` path and the params they declare. This is the source of truth used by `modules/quarto_params.nf` at runtime and validated by `bin/check_notebook_registry.py` in CI. Every param listed in the registry must have a matching variable in the notebook's `#| tags: [parameters]` cell. The Python scripts under `bin/` are not registered here, and neither are `cluster_report.qmd` or `qc_report.qmd` — they declare no parameters, taking their input from what Nextflow stages beside them.

### Params YAML flow (`modules/quarto_params.nf`)
Used by the `plot_follicle` step only. `paramsFile()` writes `<outdir>/.quarto_params/<notebook>/params_<id>.yml` and returns the path for Nextflow staging. Writing to `outdir` (NFS) rather than `/tmp` is intentional — symlinks to head-node `/tmp` break on OSCER compute nodes.

### Process conventions
- Always use `script:` blocks, never `exec:` — processes must run through SLURM.
- Every process script sets `XDG_CACHE_HOME=$PWD/.cache` and `TMPDIR=$PWD/tmp` to avoid writing to a read-only compute-node `/tmp`.
- Keep named input variables; do not inline maps into process call arguments.
- Build command lines with optional arguments using a Groovy list + conditional append:

```groovy
def myArgs = ["--required_a ${val_a}", "--required_b ${val_b}"]
if (optional_c) myArgs << "--optional_c ${optional_c}"
"""
my_script.py ${myArgs.join(' ')}
"""
```

## Adding an analysis notebook

1. Create `notebooks/analyze/<name>.qmd` with a `#| tags: [parameters]` Python cell declaring all inputs.
2. Add an entry to `assets/notebook_registry.json` with the notebook ID, relative path, and `params` list matching the parameters cell exactly.
3. Wire a new process into `modules/<name>.nf` and add a matching `--step` branch in `main.nf`.
4. Run `python bin/check_notebook_registry.py` to verify.

## Adding a create/cluster/downsample-stage script

These steps use plain Python scripts, not notebooks.

1. Create `bin/<name>.py` with an `argparse` CLI (`parse_args()` function) declaring all inputs.
2. Wire a new process into `modules/<name>.nf` and add a matching `--step` branch in `main.nf`, passing args directly.
3. No registry entry is needed.

## CI

Two GitHub Actions run on PRs to `main`:
- **Validate notebook registry** — runs `python bin/check_notebook_registry.py`
- **Stub run** — runs every `main.nf --step` with `-stub` to verify workflow wiring without executing scripts or notebooks

## Code style (`.nf` files)

- 4-space indentation
- Process names in `UPPER_SNAKE_CASE`; params, variables, CSV headers in `snake_case`
- Add file-level header comments, docstrings on helper functions, section markers, and WHY comments for non-obvious decisions
- Annotate channel shape at every `.set {}` call and after non-obvious transformations so the tuple structure is always visible without tracing back through the chain:

```groovy
.set { createSdataInputs } // tuple(sample, staged_path, he_image, he_alignment)
// createSdataRun.artifacts: tuple(sample, zarr)
```
